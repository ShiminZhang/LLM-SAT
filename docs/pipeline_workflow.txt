# Full Pipeline Workflow

This document describes the end-to-end pipeline for evolving SAT solver
heuristics using LLM-guided generation, evaluation, and genetic crossover.

## Overview

The pipeline has four major phases:

  1. Data Generation — LLM creates leader algorithms and team member variants
  2. Evaluation — Build solvers, run on benchmarks via SLURM, collect PAR2 scores
  3. Promotion — Best-performing team member replaces leader within each team
  4. Genetic Evolution — LLM-guided crossover of promoted leaders to create
     improved offspring, followed by evaluation and selection

Phases 1-3 use the original generation tag (e.g. "gemini_trial5").
Phase 4 creates new offspring under a separate output tag (e.g.
"gemini_trial5_gen1_v1") and can be iterated.

All evaluation steps use --quick-eval (100 representative CNFs, 1000s timeout)
for faster turnaround. See "Quick-Eval Mode" section for details.

## Quick-Eval Mode

All evaluation commands in this workflow use `--quick-eval`, which:
  - Evaluates on 100 representative CNFs (from data/benchmarks/satcomp2025_quick100.txt)
  - Uses 1000s timeout per CNF (~17 min) instead of the default 5000s
  - Uses 20 min SLURM wall time instead of 90 min
  - Uses PAR2 penalty of 2000 (2x quick timeout) instead of 10000

To generate the quick-eval benchmark list:
```bash
python scripts/generate_benchmark_subset.py
```

The genetic evolution pipeline (Phase 4) also uses quick-eval by default
when --evaluate is set (configured internally in evaluate_offspring()).

## Phase 1: Data Generation

### Script: `src/llmsat/pipelines/gemini_data_generation.py`

Creates the initial population of SAT solver heuristics:

  1. Generates N leader algorithms using the designer prompt
     - Each leader gets `parent_id=None` in the database
     - Temperatures interpolated from 0.5 to 1.0 for diversity

  2. For each leader, generates M member variants
     - Each member modifies a specific step of the leader's algorithm
     - Members get `parent_id=<leader_algorithm_id>` in the database

  3. Generates C code for ALL algorithms (leaders + members)

Output structure:
  outputs/<generation_tag>/batch_batches/<batch_id>/
    leaders_output.txt                     # Leader algorithms (JSONL)
    member_output_batches/<batch_id>.txt   # Member algorithms (JSONL)
    code_output_batches/<batch_id>.txt     # C code (JSONL)
    team_batch_map_<timestamp>.json        # Maps batch IDs to algorithm hashes

Database state after this phase:
  - AlgorithmResult entries for each leader (parent_id=None) and member
    (parent_id=leader_id)
  - CodeResult entries for each algorithm's generated code
  - Router table entries linking all algorithm IDs to the generation tag

## Phase 2: Evaluation

### Script: `src/llmsat/pipelines/evaluation.py`

Builds solvers and evaluates them on SAT benchmarks via SLURM.

### Step 2a: Build and submit evaluation jobs

```bash
# Build all solvers first (local compilation)
python src/llmsat/pipelines/evaluation.py \
    --run_all --generation_tag gemini_trial5 \
    --build-only

# Submit SLURM quick-eval jobs (skip rebuild)
python src/llmsat/pipelines/evaluation.py \
    --run_all --generation_tag gemini_trial5 \
    --quick-eval --batch-mode --skip-build
```

Or in one step (build + submit with quick-eval):
```bash
python src/llmsat/pipelines/evaluation.py \
    --run_all --generation_tag gemini_trial5 \
    --quick-eval --batch-mode
```

### Step 2b: Wait for SLURM jobs to complete

```bash
squeue -u $USER    # Monitor running jobs
```

### Step 2c: Collect PAR2 results

```bash
python src/llmsat/pipelines/evaluation.py \
    --collect_all_results --generation_tag gemini_trial5 --quick-eval
```

This reads solver output logs and computes PAR2 scores:
  - Solved instances: actual CPU time in seconds
  - Timeout/error instances: PAR2 penalty (2000 in quick-eval mode)
  - PAR2 score: average across all instances

## Phase 3: Promotion

### Script: `src/llmsat/pipelines/evaluation.py --promote-leaders`

After all PAR2 scores are collected, promote the best algorithm in each team:

```bash
# Preview promotions without making changes
python src/llmsat/pipelines/evaluation.py \
    --promote-leaders --generation_tag gemini_trial5 \
    --dry-run

# Execute promotions
python src/llmsat/pipelines/evaluation.py \
    --promote-leaders --generation_tag gemini_trial5
```

What promote-leaders does for each team:
  1. Compares PAR2 scores of leader vs all members
  2. If a member strictly beats the leader's PAR2:
     - Swaps filesystem directories (member -> leaders/, leader -> members/)
     - Updates database: promoted member gets parent_id=None,
       demoted leader gets parent_id=new_leader_id,
       remaining members point to new leader
  3. Writes a PAR2 summary report to outputs/<tag>/par2_scores.txt

After this phase, the database reflects the best algorithms as leaders
(parent_id=None), ready for genetic evolution.

## Phase 4: Genetic Evolution

### Script: `src/llmsat/pipelines/genetic_evolution.py`

Evolves the promoted leaders through LLM-guided crossover.

### Loading: Leaders from DB

The pipeline loads the population from the database using `load_population()`,
which by default only loads leaders (algorithms with `parent_id=None`). This
ensures that after promote-leaders has run, the genetic evolution operates on
the best algorithms from each team.

NOTE: The `--folder` flag can be used to load from output files instead, but
this reads the ORIGINAL leaders_output.txt (before promotion) and is mainly
useful for initial testing or when the DB is not available.

### Evaluation mode

When --evaluate is set, offspring are evaluated using quick-eval mode by
default (100 CNFs, 1000s timeout). This is configured internally in the
evaluate_offspring() function and does not require a CLI flag.

### Evolution loop (per iteration):

  1. Causal Analysis: LLM analyzes each leader's strengths, weaknesses,
     key mechanisms, and improvement suggestions.

  2. LLM-Proposed Combinations: A single LLM call per minibatch receives
     all leaders + their causal analyses and proposes the top-k most
     promising pairs for crossover. Pairs are scored 1-10; only pairs
     above --rubric_min proceed.

  3. Crossover: LLM combines each proposed pair of parents into an
     offspring algorithm description.

  4. Code Generation: LLM translates offspring algorithms into C code.
     Parent C code is included as structural reference.

  5. Evaluation: Build solver and submit SLURM quick-eval jobs.

  6. Selection (PAR2): Keep offspring whose PAR2 beats the best parent.
     Top-tier offspring are promoted into the population for the next
     iteration.

### Running genetic evolution:

```bash
# Iter 1: fresh start from promoted leaders
python src/llmsat/pipelines/genetic_evolution.py \
    --generation_tag gemini_trial5 \
    --output_tag gemini_trial5_gen1_v1 \
    --code_prompt_path data/prompts/coder_prompt.txt \
    --evaluate \
    --top_k 5 \
    --minibatch_size 10 \
    --rubric_min 6.0 \
    --rubric_keep_top_n 10 \
    --par2_keep_top_n 7 \
    --model gemini-3-flash-preview
```

After SLURM jobs complete, collect results and run iter 2:

```bash
# Collect iter 1 results
python src/llmsat/pipelines/evaluation.py \
    --collect_all_results --generation_tag gemini_trial5_gen1_v1_iter1 --quick-eval

# Iter 2: carries forward improvements from iter 1
python src/llmsat/pipelines/genetic_evolution.py \
    --generation_tag gemini_trial5 \
    --output_tag gemini_trial5_gen1_v2 \
    --prev_output_tags gemini_trial5_gen1_v1 \
    --code_prompt_path data/prompts/coder_prompt.txt \
    --evaluate \
    --top_k 5 --minibatch_size 10 \
    --rubric_min 6.0 --rubric_keep_top_n 10 --par2_keep_top_n 7 \
    --model gemini-3-flash-preview
```

The loop stops when:
  - No offspring improve over the best parent PAR2, OR
  - max_iterations is reached (hardcoded to 1 per invocation since SLURM
    is async; multi-iteration is driven by re-running with --prev_output_tags)


========================================================================
                    ITERATIVE PIPELINE
========================================================================

The sections above describe the linear pipeline (Phases 1-4). The
sections below describe the ITERATIVE pipeline, which allows you to
refine leaders through repeated mutation cycles and feed genetic
evolution offspring back into the mutation loop.


# Iterative Pipeline Overview

The iterative pipeline separates the linear pipeline into two
independent loops connected by a bridge:

  Loop A: Leader Refinement (runs N times)
    Generates new mutants for existing leaders, evaluates them, and
    promotes the best. The leaders get stronger each iteration without
    generating new leaders from scratch.

  Loop B: Genetic Evolution (runs once)
    Takes refined leaders and crosses them over to produce offspring.
    Same as Phase 4 above — no changes to this step.

  Bridge: GE → Loop A
    Takes the top N offspring from genetic evolution and converts them
    into clean leaders. These leaders then enter Loop A for further
    refinement.

The overall cycle looks like:

  Initial Generation (Phase 1)
        |
        v
  Loop A  (mutate → evaluate → promote) x N
        |
        v
  Loop B  (genetic evolution, once)
        |
        v
  Bridge  (top offspring → new leaders)
        |
        v
  Loop A  (mutate → evaluate → promote) x N
        |
        v
  Loop B  ...
        |
  (repeat as needed)


# Generation Tag Naming Convention

Each iteration step uses its own generation tag so that algorithms
from different iterations don't mix. Tags follow this pattern:

  {base}_iter0     Initial leaders (from Phase 1 or from Bridge)
  {base}_iter1     After 1st mutant→evaluate→promote cycle
  {base}_iter2     After 2nd cycle
  ...
  {base}_ge1       Genetic evolution output
  {base}_ge1_iter0 GE offspring promoted to leaders (Bridge output)
  {base}_ge1_iter1 After 1st Loop A refinement of GE offspring
  ...

Example for a full run:

  gemini_trial5          Original generation (Phase 1)
  gemini_trial5_iter1    Loop A iteration 1
  gemini_trial5_iter2    Loop A iteration 2
  gemini_trial5_iter3    Loop A iteration 3 (leaders are now refined)
  gemini_trial5_gen1_v1  Genetic evolution output
  gemini_trial5_ge1_iter0  Bridge: top GE offspring as leaders
  gemini_trial5_ge1_iter1  Loop A on GE offspring, iteration 1
  gemini_trial5_ge1_iter2  Loop A on GE offspring, iteration 2


# Loop A: Leader Refinement

## What it does

Loop A takes an existing set of leaders and repeatedly:
  1. Generates new mutant variants for each leader
  2. Evaluates ONLY the new mutants (leaders keep their existing scores)
  3. Promotes the best algorithm in each team to leader

Leaders are never regenerated. They only change through promotion —
if a mutant outperforms its leader on PAR2, they swap roles.

## Script: run_loop_a.sh

Usage:
  ./run_loop_a.sh <base_tag> <n_iterations> [source_tag]

Arguments:
  base_tag       Base name for iteration tags. Each iteration creates
                 {base_tag}_iter1, {base_tag}_iter2, etc.
  n_iterations   How many mutate→evaluate→promote cycles to run.
  source_tag     (Optional) Where to load the initial leaders from.
                 Defaults to {base_tag}_iter0.

Environment variables:
  POLL_INTERVAL  Seconds between SLURM status checks (default: 120)
  M_VARIANTS     Mutant variants per leader (default: 3)
  MODEL          Gemini model name (default: gemini-3-flash-preview)

Examples:

  # Refine initial leaders 3 times
  ./run_loop_a.sh gemini_trial5 3

  # Refine GE offspring (loaded from bridge output)
  ./run_loop_a.sh gemini_trial5_ge1 3 gemini_trial5_ge1_iter0

  # Use more mutants and a different model
  M_VARIANTS=5 MODEL=gemini-3.1-pro-preview ./run_loop_a.sh gemini_trial5 3

## What happens each iteration

For iteration i (tag = {base_tag}_iter{i}):

  Step 1: gemini_data_generation.py --mutants-only
    - Loads leaders from the previous iteration's tag
    - Registers those leaders under the new iteration tag
    - Generates M mutant variants per leader (LLM call)
    - Generates C code for each mutant (LLM call)
    - Leaders' existing code is untouched

  Step 2: evaluation.py --run_all --skip-evaluated
    - Builds Kissat solvers for new mutants only
    - Leaders are skipped because their code already has PAR2 scores
    - Submits SLURM job arrays for the new mutants
    - Writes job IDs to outputs/{tag}/submitted_job_ids.json

  Step 3: SLURM polling
    - Reads submitted_job_ids.json
    - Polls squeue every POLL_INTERVAL seconds
    - Waits until all jobs finish

  Step 4: evaluation.py --collect_all_results
    - Parses solving logs, computes PAR2 for each mutant

  Step 5: evaluation.py --promote-leaders
    - Compares leader PAR2 vs member PAR2 in each team
    - If a mutant beats the leader, they swap roles in the DB
    - Leaders are now the best-known algorithms

If you prefer to run each step yourself:

  # Repeat with --source_tag gemini_trial5_iter1 -> --output_tag gemini_trial5_iter2


# Bridge: Genetic Evolution → Loop A

## What it does

After genetic evolution produces offspring, the Bridge takes the top N
offspring (ranked by PAR2) and converts them into clean leaders that
can enter Loop A. This REPLACES the leader pool — only the selected
offspring become leaders.

The bridge preserves lineage: each offspring's original parent IDs are
saved in the algorithm's other_metrics field before being cleared.

## Script: run_bridge.sh

Usage:
  ./run_bridge.sh <ge_output_tag> <target_base_tag> [top_n]

Arguments:
  ge_output_tag    The generation tag where GE offspring were stored
                   and evaluated (e.g., gemini_trial5_gen1_v1_iter1).
  target_base_tag  Base name for the new leader pool. Leaders are
                   registered under {target_base_tag}_iter0.
  top_n            (Optional) How many top offspring to promote.
                   Default: 10.

Examples:

  # Take top 10 offspring, then refine with 3 Loop A iterations
  ./run_bridge.sh gemini_trial5_gen1_v1_iter1 gemini_trial5_ge1 10
  ./run_loop_a.sh gemini_trial5_ge1 3 gemini_trial5_ge1_iter0

  # Take top 5 offspring only
  ./run_bridge.sh gemini_trial5_gen1_v1_iter1 gemini_trial5_ge1 5

## Running the bridge manually

  python src/llmsat/pipelines/genetic_evolution.py \
      --promote-offspring \
      --source_tag gemini_trial5_gen1_v1_iter1 \
      --target_tag gemini_trial5_ge1_iter0 \
      --top_n_promote 10

# How --skip-evaluated Works

When running evaluation with --skip-evaluated, the pipeline checks
each code result's PAR2 score in the database BEFORE building or
submitting SLURM jobs:

  - If CodeResult.par2 is not None → skip (already scored)
  - If CodeResult.par2 is None → build and evaluate normally

This is critical for Loop A efficiency: leaders carry their PAR2
scores from previous iterations (stored globally on the CodeResult),
so only newly-generated mutants need evaluation. Without this flag,
leaders would be redundantly rebuilt and re-evaluated every iteration.

PAR2 scores are stored on CodeResult objects in the database, not
tied to a specific generation tag. This means a leader's score
persists even when the leader is registered under a new iteration tag.


# How SLURM Polling Works

When evaluation.py submits SLURM job arrays, it now saves the job
IDs to:

  outputs/{generation_tag}/submitted_job_ids.json

Format: {"job_ids": [12345, 12346, ...], "timestamp": "..."}

The run_loop_a.sh script reads this file and polls squeue until all
listed jobs are no longer running or pending. If the file doesn't
exist (e.g., no jobs were submitted because all code was already
evaluated), polling is skipped.

If you're running manually, you can poll with:
  squeue -j 12345,12346 -h    # empty output means jobs are done


# Important Notes

  - The router table maps each algorithm to exactly ONE tag at a time.
    When Loop A moves a leader to a new iteration tag, it disappears
    from the old tag. This is expected — each iteration is a
    self-contained snapshot. Old mutants remain under their original
    tag as historical records.

  - Promotion is safe to run multiple times. If no member beats the
    leader, nothing changes. Running promote-leaders on an already-
    promoted tag is a no-op.

  - The Bridge (--promote-offspring) sets parent_id=None on selected
    offspring so they're recognized as leaders by all downstream code.
    Original parent IDs are preserved in other_metrics["original_parent_ids"]
    for traceability.

  - If a mutant across two iterations happens to have an identical
    description (same SHA256 hash), it will share the same algorithm_id.
    The database upsert overwrites the old entry. This is rare with
    LLM-generated content but worth knowing.
